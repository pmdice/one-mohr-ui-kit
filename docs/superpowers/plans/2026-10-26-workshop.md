# Werkstatt-Ansicht (Teil 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tablet-Ansicht für die Station nach W-01–W-08 (Station am Gerät, Kamera als Seite mit Ersatz-Eingabe, grosse Rückmeldung mit Ton, Kurzinfo, Fehler mit nächstem Schritt, Warteschlange ohne Netz, „Jetzt hier“), ein Beispiel mit simulierter Kamera und die Regeln im Handbuch.

**Architecture:** Neue Komponenten unter `components/workshop/`. Kamera, Detektor, Ton und Speicher kommen als Props/Funktionen herein (testbar, ersetzbar). Scan-Logik und Laufzettel-Modell aus Teil 4 (`components/status/scan.ts`, `components/status/examples/slip.ts`) werden wiederverwendet.

**Tech Stack:** wie Teil 1–4.

**Spec:** `docs/superpowers/specs/2026-10-26-workshop-design.md`

## Global Constraints

- Nur Tokens aus `app/tokens.css`; Guard-Test gilt.
- Wurzel der Werkstatt-Ansicht trägt `data-density="comfortable"`; Ziele ≥ 48 px (`min-h-12`), Hauptinfo ≥ 20 px (`text-xl`).
- Kein Hover als einziger Weg, keine Tooltips, Icons `aria-hidden` + Text.
- localStorage in try/catch; Schlüssel `workshop:station`, Warteschlange `workshop:queue`.
- Rückgängig eines Scans 10 s; Doppel-Scan-Sperre 3 s (aus S-07).
- Regeltexte Deutsch, Code Englisch.

## Review Focus

1. **Kamera-Stream bleibt an:** Verlassen der Ansicht / Wechsel in Ersatz-Eingabe → alle Tracks gestoppt. → Test Task 2.
2. **Derselbe Code bleibt im Bild:** Detektor liefert ihn 20× hintereinander → nur ein `onCode`; erst nachdem er 1 s nicht mehr erkannt wurde, wieder. → Test Task 2.
3. **Warteschlange und Neuladen:** Offline-Scans überleben ein Neuladen (localStorage), werden genau einmal gesendet. → Test Task 1.
4. **Scan zurücknehmen nach Offline-Scan:** noch nicht gesendeter Scan wird aus der Warteschlange entfernt statt eine Gegenbuchung zu senden. → Test Task 1/4.
5. **Station wechseln während Scans warten:** wartende Scans behalten ihre ursprüngliche Station. → Test Task 1.

### Task 1: scanQueue, useStation

- `type QueuedScan = { id: string; code: string; station: string; at: number; error?: string }`
- `createScanQueue({ storage?: Storage | null, key = "workshop:queue", send: (scan) => Promise<{ ok: true } | { ok: false; reason: string }> })` → `{ items(): QueuedScan[]; add(scan: Omit<QueuedScan, "id" | "error">): QueuedScan; remove(id): boolean; flush(): Promise<void>; subscribe(fn): () => void }`
  - `add` speichert sofort (storage, try/catch). `flush` sendet der Reihe nach; `ok` → entfernen; `ok:false` → bleibt mit `error`, wird beim nächsten `flush` übersprungen; Netzfehler (Promise rejected) → abbrechen, Rest bleibt. Gleichzeitige `flush`-Aufrufe laufen nicht doppelt.
  - Beim Erzeugen liest die Queue den gespeicherten Stand (Review Focus 3).
- `useStation(storage?)` → `[station: string | null, setStation(id | null)]`, Schlüssel `workshop:station`, werfendes Storage → nur im Speicher.
- Tests: add/flush Reihenfolge + Originalzeit; Ablehnung bleibt mit Grund und blockiert nicht; Netzfehler bricht ab, zweiter flush sendet genau einmal; Neuladen (neue Queue, gleiches Storage) liest Stand; parallele flush senden nicht doppelt; remove entfernt; Station der wartenden Scans bleibt (Review Focus 5); useStation speichert und überlebt werfendes Storage.

### Task 2: CameraScanner

- `type Detector = { detect(source: HTMLVideoElement): Promise<{ rawValue: string }[]> }`
- `CameraScanner({ onCode(code), getStream?: () => Promise<MediaStream>, createDetector?: () => Detector | null, interval = 250, fallback: React.ReactNode, simulated?: React.ReactNode })`
  - Standard `getStream` = `getUserMedia({ video: { facingMode: "environment" } })`, `createDetector` = `new BarcodeDetector({ formats: ["qr_code", "code_128", "code_39"] })` falls vorhanden, sonst `null`.
  - Zustände: `starting` („Kamera startet …“), `active` (Video + Rahmen, `aria-label="Kamera"`), `denied` („Kamera nicht erlaubt. In den Einstellungen des Browsers die Kamera für diese Seite erlauben.“), `unsupported` („Dieses Gerät erkennt Codes nicht selbst. Nummer unten eintippen oder Hand-Scanner nutzen.“); `fallback` (das Eingabefeld) wird immer gerendert.
  - Gleicher Code wird nur einmal gemeldet, bis er ≥ 1 s nicht erkannt wurde (Review Focus 2).
  - Unmount → `stream.getTracks().forEach(t => t.stop())`, Intervall gestoppt (Review Focus 1).
  - `simulated` ersetzt Stream und Detektor (für das Beispiel).
- Tests mit Fake-Stream/Detektor + Fake-Timern: active ruft onCode einmal bei 20 gleichen Treffern; nach 1 s Pause erneut; denied-Text bei `NotAllowedError`; unsupported bei `createDetector → null`; Tracks gestoppt beim Unmount.

### Task 3: ScanBanner, tones, SlipCard, HereList

- `tones.ts`: `playTone(kind: "in" | "out" | "error")` mit Web Audio (in: 880 Hz 120 ms; out: 2× 660 Hz; error: 220 Hz 300 ms), still wenn kein `AudioContext`; `vibrate(kind)` über `navigator.vibrate` wenn vorhanden.
- `ScanBanner({ result: { kind: "in" | "out" | "error"; title: string; message: string; next?: string } | null, sound = true, play = playTone, onUndo?, undoUntil?, now })` – Volle Breite, `text-3xl` Wort (EIN / AUS / FEHLER), Satz, nächster Schritt; `role="status"` bzw. `role="alert"`; spielt Ton bei neuem Ergebnis (`play` einmal je Ergebnis), nicht wenn `sound=false`; Knopf „Scan zurücknehmen“ (`min-h-12`) solange `onUndo` gesetzt.
- `SlipCard({ number, customer, material, pieces, urgency: StatusDef-artiges { label; tone }, notes?: string[] })` – genau diese fünf Angaben als `<dl>`, Hinweise als `role="note"` Warnung darüber.
- `HereList({ station: string; items: { id; number; since: number; norm?: number }[]; now; onSelect(id) })` – Überschrift „Jetzt an {Station} ({n})“, längste zuerst, Dauer + `overdueHint`, Einträge sind Knöpfe `min-h-12`; leer → „Nichts eingescannt“.
- Tests: Banner Rollen/Wort/Ton einmal/stumm/Undo-Knopf; SlipCard fünf Angaben + Hinweis; HereList Reihenfolge + Warnung + Auswahl + leer.

### Task 4: StationHeader, StationPicker, Beispiel

- `StationPicker({ stations, onPick })` – Überschrift „An welcher Station steht dieses Tablet?“, je Station grosser Knopf.
- `StationHeader({ station: string; waiting: number; online: boolean; sound: boolean; onSoundChange; onChangeStation })` – Stationsname `text-2xl`, „Ton an/aus“ (`aria-pressed`), Warteanzeige „{n} Scan(s) warten auf Verbindung“ (`role="status"`) wenn > 0, „Station wechseln“ rechts aussen → `ConfirmDialog` (aus Teil 4) „Station wechseln?“ mit Folge „Alle folgenden Scans zählen an der neuen Station.“
- `WorkshopTablet({ initial?: "default" | "setup" | "denied" | "offline", now? })` – nutzt `seedWorld`/`applyEvent`/`resolveScan` aus Teil 4; simulierte Kamera: Kamerafläche mit Rahmen und Beschriftung „Simulation: Zettel antippen = vor die Kamera halten“, Knöpfe für die 4 Zettel + „Unbekannter Code“; Verbindungsschalter; Scan → `resolveScan` → Ergebnis in Banner, Karte, Queue (online: sofort angewendet; offline: in Queue, Banner „gespeichert, wird gesendet“, beim Verbinden flush → applyEvent); Undo 10 s: wartender Scan → aus Queue entfernt, gesendeter → Gegenscan; Fehlertexte nach W-06; Hinweise für 26100013-1 („Steine nicht mitgiessen“).
- Stories `Werkstatt/Beispiel: Tablet an der Station`: Standard, Erste Einrichtung, Kamera verweigert, Ohne Verbindung (3 wartende Scans).
- Tests: Einrichtung → Station gewählt → Kopf zeigt sie; Scan 3/4 → EIN + Karte + Liste „Jetzt an Guss (2)“; unbekannter Code → Fehler mit nächstem Schritt; offline Scan → „1 Scan wartet auf Verbindung“, Verbindung an → weg und Liste aktualisiert; Scan zurücknehmen (online und offline, Review Focus 4); Station wechseln braucht Bestätigung; denied-Variante zeigt Eingabe und funktioniert.
